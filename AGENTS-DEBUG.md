# AGENTS-DEBUG.md

## Scope

- This file supplements `AGENTS.md` for debug and Playwright-related work.

## Debug Workflow

- Build the Playwright-enabled debug image with `./bake-docker.sh -i debug`. The resulting local image is `cmucal/cabot-debug:latest` unless another tag is selected by the build flow.
- For a private GitHub Issue debug request, the default entrypoint is `./cabot_debug/script/codex_issue_debug.sh <github-issue-url>` from the repository root.
- Run `box_download_logs.mjs` in the `debug` service, not on the host directly.
  - Typical invocation from the repository root:
    - `docker compose exec -u developer debug bash -lc 'node cabot_debug/script/box_download_logs.mjs <github-issue-url>'`
  - The helper script for downloaded archives is `cabot_debug/script/download-helper.sh`.
- For Playwright changes, verify inside the `debug` container rather than assuming host behavior.
- If a browser automation flow depends on persistent login, reuse the profile under `docker/home/.box-profile` inside the container.
- After logs are downloaded, prefer ROS-native inspection over raw file greps when bag data is present.
- If `host_ws/install/setup.bash` exists, source it before using `ros2` CLI tools or repo-local ROS Python tools.
- Start bag inspection with commands such as `ros2 bag info` and topic-level checks so you know which bag files, topics, and time ranges actually contain the event you are explaining.
- Before writing one-off parsing commands, check whether an existing helper under `cabot_debug/src`, `cabot_debug/*.sh`, or `cabot_debug/launch` already covers the needed inspection.
- If bag inspection is expected but cannot be performed, say exactly why, for example missing environment setup, unreadable bag metadata, or unavailable tooling.

## Issue Analysis Rules

- Prefer `gh` queries that extract public links first, then inspect the linked public PRs or commits to understand the actual patch.
- If logs are required, download them with the `debug` container workflow above; do not copy Box paths, private issue numbers, operator names, or venue-specific internal notes into this file.
- When summarizing a past incident, record only the generalized symptom, the public patch, and the first logs/topics/config to inspect when it happens again.
- For open-issue triage, default to code-level analysis when local logs, bags, config, or source are available. Do not stop at generic advice if you can trace the behavior to a concrete code path, parameter, state machine, or stale state transition.
- When the issue depends on runtime behavior, use bag evidence, text logs, and code together when they are available. Do not rely on only one of those three if the others can still sharpen the explanation.
- For bag-backed claims, identify the specific bag file and topics that support the claim, then connect those observations to the responsible code path or state machine.
- Before posting a GitHub comment, try to rule out at least one plausible alternative explanation. If the root cause is still uncertain, state the strongest hypothesis, the competing hypothesis, what evidence supports each, and the single next check that would separate them.
- Prefer comments that answer "what actually happened here?" over comments that only say "please inspect X." A useful triage comment should narrow the problem, not just restate the debugging checklist.
- If enough evidence exists to identify a likely bad transition, stale state, contradictory input source, wrong configuration path, or likely patch point, say that explicitly even when the issue remains `human_validation_required`.

## Codex Output And Triage

- Every GitHub issue comment generated by Codex must begin with a short disclosure line such as `Codex auto-generated analysis:`. Put this on the first line, not at the end.
- Every PR title or body text generated by Codex must also begin with an explicit disclosure that it is Codex-generated and may need human verification.
- Do not hide or soften the disclosure. Readers should be able to tell immediately that the text or PR draft was produced automatically.
- Goal: classify each issue as either `codex_pr_ok` or `human_validation_required`.
- Default rule: if the answer is ambiguous, classify it as `human_validation_required`.
- Primary criterion: the question is not "can Codex edit the code", but "can the effect of the shipped change be validated without a developer or operator checking real robot behavior".
- `human_validation_required` is a validation label, not a ban on code analysis, code changes, or PR creation. It means the remaining confidence gap is in behavioral validation, deployment validation, or field confirmation.
- Even for `human_validation_required`, Codex should still analyze the relevant implementation path by default and may prepare a narrow PR when there is a concrete candidate fix, instrumentation improvement, or guardrail change. The PR and issue comment must clearly separate:
  - what was validated automatically
  - what still needs human or robot verification
- Avoid speculative wide runtime tuning when the evidence chain is weak. If the safest action is still only a comment, explain why no specific patch is justified yet.

### `codex_pr_ok`

- Use this only when all of the following are true:
  - The failure is deterministic and host-observable: build failure, startup crash, exception, missing dependency, bad script behavior, wrong file lookup, broken API wiring, or logging/debug tooling issue.
  - The success condition is machine-checkable by CI, local command output, unit/integration test, or static inspection.
  - The change does not alter robot motion semantics, localization behavior, perception thresholds, hardware timing, or site-specific map behavior.
  - The change does not require physical devices, phones, sensors, cloud credentials, remote.it, or field environment access to know whether it is correct.
  - A wrong fix would not silently create unsafe motion or degraded navigation in the field.

### `human_validation_required`

- Use this if any of the following are true:
  - The issue is about collision, stopping distance, obstacle avoidance, people avoidance, speed control, planner behavior, elevator behavior, crosswalk behavior, or any other robot motion outcome.
  - The issue is about localization drift, wrong floor selection, GNSS/RTK recovery, scan matching, pressure-based floor changes, or map/site parameter tuning.
  - The issue is about perception quality or timing: people detection, tracking merge/split behavior, stop reasons, announcement timing, read timing, or threshold tuning.
  - The issue depends on field logs or operator reports describing behavior such as "too close", "did not say", "sometimes", "random", "unstable", "drifts", or "works better/worse".
  - The proposed fix changes thresholds, filters, topics, footprints, costmap layers, site data, or environment variables that affect runtime navigation behavior.
  - The issue spans multiple devices or services and needs end-to-end workflow confirmation, even if it does not directly change motion.
  - The acceptance criterion is behavioral rather than binary, for example "more stable", "safer", "earlier", "less random", or "better timing".
- This classification does not prevent Codex from preparing a PR. It means the PR cannot be treated as fully verified until a human validates the runtime outcome.

## Sanitized Fix Patterns

- Use this section as a quick repository/function map when deciding where related code is likely to live.
- Multi-floor localization, floor transitions, scan matching, GNSS recovery, and altitude-manager behavior are usually under `cabot-navigation`, especially `mf_localization/`, localization launch/config, and matching site parameters in `cabot_sites*`.
- Route progression, elevator goals, navigation task state, app-facing events, stop reasons, speech timing, and social-navigation behavior are usually under `cabot-navigation/cabot_ui` or `cabot-navigation/cabot_ui_plugins`.
- Planner/controller behavior, BT execution, local costmaps, obstacle avoidance, and navigation runtime parameters are usually under `cabot-navigation/cabot_navigation2` plus its launch and parameter files.
- Signal or crosswalk behavior often spans multiple repositories: navigation-side logic is usually in `cabot-navigation/cabot_ui`, service integration may be in `cabot-app-server`, and reproducibility or map-side tuning may be in `cabot_sites*`.
- Footprint shape, common topic utilities, and image throttling are usually in `cabot-common`; navigation code may only consume those interfaces or parameters.
- Lidar speed control, low-level sensors, serial/CAN handling, IMU behavior, and robot-specific hardware diagnostics are usually in `cabot-drivers`, with higher-level aggregation or launch wiring in `cabot-navigation`.
- Handle, touch, feature-plugin, and runtime parameter propagation issues are usually in `cabot-navigation/cabot_ui`, `cabot-navigation/cabot_ui_plugins`, or related plugin startup code.
- Locale handling, spoken message selection, POI lookup distance, and facility read timing are usually in `cabot-navigation/cabot_ui`, while facility-specific values and map annotations are often in `cabot_sites*`.
- Site-specific floor heights, pressure thresholds, scan-recovery tuning, global-localization assets, ENU/GNSS alignment, and facility metadata usually belong in `cabot_sites*` before changing core navigation code.
- Indoor GNSS/NTRIP startup, localization container behavior, and related runtime scripts are usually in `cabot-navigation/docker/` or adjacent localization launch scripts, not in the top-level meta-repo.
- Camera/debug bag-size controls, debug-data collection, and host-side analysis helpers are often split between `cabot-common`, `cabot-navigation` launch/config, and top-level tooling in `cabot` or `cabot_debug`.
- GUI startup, RViz launch races, Docker image wiring, compose behavior, local registry handling, and dependency setup are usually in the top-level `cabot` repository or `cabot-navigation/docker/`.
